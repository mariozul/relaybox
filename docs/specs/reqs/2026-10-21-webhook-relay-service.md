# ReqSpec: Relaybox — Multi-Tenant Webhook Relay Service (TRD: relaybox-trd)\n\n## 1. Executive Summary\nThis document expands upon the provided Technical Requirements Document (TRD: `relaybox-trd`) for the Relaybox service. Relaybox will be a standalone Go service designed to reliably ingest domain events, persist them durably using a transactional outbox pattern, and relay them to registered external subscriber endpoints with retries, idempotency, and strict multi-tenant isolation. It focuses on durable, at-least-once delivery without event loss and incorporates production-grade observability.\n\n## 2. Functional Requirements (FRs)\n\n### 2.1. Ingestion\n- **FR-ING-01: Event Ingestion Endpoint**\n    - Description: Expose a `POST /v1/events` HTTP endpoint that accepts a JSON payload containing `event_type` (string), `payload` (arbitrary JSON object), and `dedup_key` (string, optional).\n    - Constraint: Tenant identity MUST be resolved from the authenticated request context (e.g., JWT, API key header), never directly from the request body or query parameters (RULE-SEC-01).\n- **FR-ING-02: Transactional Event Persistence & Outbox**\n    - Description: The persistence of an event and its enqueuing for delivery (by writing to an outbox table) MUST occur within a single atomic database transaction (RULE-DATA-01).\n    - Constraint: Direct remote event publication (e.g., to a message broker or external service) is strictly forbidden *inside* an open database transaction before commit (RULE-EVT-02).\n- **FR-ING-03: Idempotent Event Ingestion**\n    - Description: The ingestion process MUST be idempotent. If the same `(tenant_id, dedup_key)` is received multiple times, it must result in the creation of exactly one event record and subsequent delivery attempts. This ensures safe re-execution without duplicate side effects (RULE-DATA-02).\n\n### 2.2. Subscriptions\n- **FR-SUB-01: Subscription Management Endpoints**\n    - Description: Provide CRUD (Create, Read, Update, Delete) HTTP endpoints for managing subscriber subscriptions. This includes `POST /v1/subscriptions` (create), `GET /v1/subscriptions/{id}` (read), `PUT /v1/subscriptions/{id}` (update), and `DELETE /v1/subscriptions/{id}` (delete). Each subscription will include `tenant_id`, `event_type`, and `target_url`.\n- **FR-SUB-02: Secure Tenant-Aware Subscription Access**\n    - Description: Access to subscription resources (create, read, update, delete) MUST enforce strict multi-tenant isolation. A tenant can only access/manage subscriptions belonging to its authenticated `tenant_id`. Tenant identity MUST be resolved from authenticated request context (RULE-SEC-01).\n\n### 2.3. Delivery\n- **FR-DEL-01: Event Delivery Mechanism**\n    - Description: Events will be delivered to the `target_url` of registered subscriptions via HTTP POST requests.\n    - Constraint: All outbound HTTP calls MUST propagate OpenTelemetry tracing context (RULE-OBS-02). The HTTP client MUST incorporate a timeout mechanism. Use of `context.Background()` or `context.TODO()` is strictly forbidden in the dispatcher or any business logic handling delivery; `ctx context.Context` MUST be passed through (RULE-RES-01).\n- **FR-DEL-02: At-Least-Once Delivery & Retry Policy**\n    - Description: The delivery mechanism MUST guarantee at-least-once delivery.\n    - Policy:\n        - A `2xx` HTTP response from the subscriber's endpoint marks the delivery attempt as successful.\n        - Transient failures (e.g., network timeouts, `5xx` HTTP status codes) will trigger retries with an exponential backoff strategy.\n        - Permanent failures (e.g., `4xx` HTTP status codes) will cause the event to be dead-lettered after a configurable maximum number of retry attempts.\n    - Constraint: Response bodies from outbound HTTP calls MUST be closed immediately after use via `defer resp.Body.Close()` (RULE-RES-03).\n- **FR-DEL-03: Bounded Concurrency for Delivery**\n    - Description: The event dispatcher/worker pool responsible for making outbound delivery attempts MUST use a bounded worker pool.\n    - Constraint: The lifecycle of all background goroutines within the worker pool MUST be tied to parent context cancellation and graceful shutdown signals; spawning unbounded goroutines is strictly forbidden (RULE-RES-02).\n- **FR-DEL-04: Idempotent Delivery Attempts**\n    - Description: Delivery attempts, from the subscriber's perspective, MUST be idempotent. Each delivery attempt originating from Relaybox will include a stable `X-Relaybox-Delivery-Id` HTTP header, ensuring that subscribers can safely process duplicate deliveries without adverse side effects (RULE-DATA-02).\n\n### 2.4. Observability & Health\n- **FR-OBS-01: Standard Health Endpoints**\n    - Description: The service MUST expose `/livez` (liveness probe) and `/readyz` (readiness probe) HTTP endpoints.\n    - Constraint: The `/readyz` endpoint MUST check connectivity to critical dependencies, specifically the PostgreSQL database (RULE-OBS-04).\n- **FR-OBS-02: Production-Grade Telemetry**\n    - Description: The service MUST emit structured JSON logs bound to `ctx context.Context` for all operations (RULE-OBS-01). Prometheus metrics MUST be exposed for request durations (e.g., `http_request_duration_seconds`) and delivery outcomes (e.g., `webhook_delivery_total`).\n    - Constraint: Prometheus metric labels for delivery outcomes MUST use bounded-cardinality values, such as `status="delivered|failed|deadletter"` (RULE-OBS-03). Unbounded labels are forbidden.\n\n## 3. Non-Functional Requirements (NFRs)\n- **NFR-01: Performance (Latency)**: p99 latency for `POST /v1/events` must be < 50ms under 1000 RPS.\n- **NFR-02: Scalability**: The system must be able to process 5000 events/second.\n- **NFR-03: Durability**: Zero event loss under process restarts (guaranteed by transactional outbox).\n- **NFR-04: Security**: Strict multi-tenancy enforced at API gateway and application layer.\n\n## 4. Acceptance Criteria (ACs)\n- **AC-01 (FR-ING-03)**: Given the system is running, When two identical `POST /v1/events` requests with the same `(tenant_id, dedup_key)` are sent consecutively, Then exactly one event row is created in the database and the same event ID is returned for both requests.\n- **AC-02 (FR-ING-02)**: Given an event is received, When the process is gracefully shut down (or crashes) immediately after the event is persisted but before its delivery attempt, Then upon restart, the event is picked up from the outbox and eventually delivered.\n- **AC-03 (FR-DEL-02)**: Given an event delivery attempt is made, When the subscriber responds with a `500` HTTP status, Then the delivery is retried with exponential backoff. When the subscriber responds with a `200` HTTP status, Then the delivery is marked successful. When the subscriber consistently responds with a `400` HTTP status after `N` retries, Then the event is moved to a dead-letter state.\n- **AC-04 (FR-SUB-02)**: Given a user belonging to `tenant_A` attempts to `GET /v1/subscriptions/{id}` where `{id}` belongs to `tenant_B`, Then the request is rejected with an appropriate authorization error (e.g., 403 Forbidden or 404 Not Found), adhering to RULE-SEC-01.\n- **AC-05 (FR-DEL-03)**: Given the delivery worker pool is configured with a maximum concurrency of `M` workers, When `M+K` events are ready for delivery, Then only `M` delivery attempts are in flight concurrently, and `K` events are queued, adhering to RULE-RES-02.\n- **AC-06 (FR-OBS-01)**: Given the PostgreSQL database is unreachable, When `/readyz` is queried, Then it returns a `503 Service Unavailable` status. When the database is reachable, Then `/readyz` returns a `200 OK` status.\n\n## 5.
