# Requirements Specification: Relaybox - Multi-Tenant Webhook Relay Service\n\n## 1. Functional Requirements\n\n*   **FR-ING-01: Event Ingestion Endpoint**\n    *   **Description**: Expose `POST /v1/events` to accept a JSON event `{ event_type, payload, dedup_key }`. Tenant identity MUST be resolved from the authenticated request context, never the body.\n    *   **AC-ING-01**: Given an authenticated tenant, when a valid event is POSTed to `/v1/events`, then the service returns a 201 Created with the event ID and the event is durably persisted.\n    *   **AC-ING-02**: Given an unauthenticated request, when POSTed to `/v1/events`, then the service returns a 401 Unauthorized.\n*   **FR-ING-02: Atomic Event Persistence & Enqueueing**\n    *   **Description**: Persisting an event and enqueuing it for delivery MUST occur in a single database transaction, writing to an outbox table (RULE-EVT-02). No remote publish inside the open transaction.\n    *   **AC-ING-03**: Given a valid event, when ingested, then exactly one event row and one outbox row are created in a single transaction.\n    *   **AC-ING-04 (AC-02 in TRD)**: Given an event is persisted and enqueued, when the service process is killed before delivery, then the event is still delivered after service restart.\n*   **FR-ING-03: Idempotent Ingestion**\n    *   **Description**: Ingestion MUST be idempotent per `(tenant_id, dedup_key)` via a unique constraint (RULE-DATA-02). Re-sends return the original event id.\n    *   **AC-ING-05 (AC-01 in TRD)**: Given the same `(tenant_id, dedup_key)` is ingested twice, then exactly one event row is created, and the second request returns a 200 OK with the original event ID.\n*   **FR-SUB-01: Subscription CRUD Endpoints**\n    *   **Description**: Expose CRUD `POST/GET/DELETE /v1/subscriptions` mapping an `event_type` to a target URL for the authenticated tenant.\n    *   **AC-SUB-01**: Given an authenticated tenant, when a valid subscription is created via `POST /v1/subscriptions`, then it returns 201 Created and the subscription is persisted.\n    *   **AC-SUB-02**: Given an authenticated tenant, when fetching subscriptions via `GET /v1/subscriptions`, then all owned subscriptions are returned.\n    *   **AC-SUB-03**: Given an authenticated tenant, when deleting an owned subscription via `DELETE /v1/subscriptions/{id}`, then it returns 204 No Content and the subscription is removed.\n*   **FR-SUB-02: Tenant-Scoped Subscriptions**\n    *   **Description**: Subscriptions are scoped strictly to the owning tenant; a tenant can never read or mutate another tenant's subscriptions (RULE-SEC-01).\n    *   **AC-SUB-04 (AC-04 in TRD)**: Given Tenant A attempts to fetch Tenant B's subscription, then the service returns 404 Not Found or 403 Forbidden.\n*   **FR-DEL-01: Background Event Dispatcher**\n    *   **Description**: A background dispatcher reads pending outbox rows and sends an HTTP POST to each matching subscriber URL. All outbound calls MUST propagate `ctx` and OpenTelemetry trace metadata (RULE-RES-01, RULE-OBS-02) and set a timeout; `context.Background()` is forbidden in the dispatcher (RULE-RES-01).\n    *   **AC-DEL-01**: Given a pending outbox row, when the dispatcher processes it, then an HTTP POST request is sent to the subscriber URL with appropriate headers and tracing.\n*   **FR-DEL-02: At-Least-Once Delivery with Retry & DLQ**\n    *   **Description**: Delivery is at-least-once. A 2xx response marks the row delivered; a transient failure (timeout, 5xx) is retried with exponential backoff; a permanent failure (4xx) is dead-lettered after N attempts. Response bodies MUST be closed immediately (RULE-RES-03).\n    *   **AC-DEL-02 (AC-03 in TRD)**: Given a subscriber returns 500 then 200, when the dispatcher retries, then the event is delivered exactly once.\n    *   **AC-DEL-03**: Given a subscriber returns 400 after N attempts, when the dispatcher processes it, then the event is moved to a dead-letter state.\n*   **FR-DEL-03: Bounded Concurrency for Dispatcher**\n    *   **Description**: The dispatcher MUST use a bounded worker pool tied to context cancellation and graceful shutdown; no unbounded goroutines (RULE-RES-02).\n    *   **AC-DEL-04 (AC-05 in TRD)**: Given concurrent ingestion and delivery load, when the dispatcher is active, then the Go race detector passes without errors.\n*   **FR-DEL-04: Idempotent Delivery Attempts**\n    *   **Description**: Delivery attempts MUST be idempotent from the subscriber's view: each attempt sends a stable `X-Relaybox-Delivery-Id` header (RULE-DATA-02).\n    *   **AC-DEL-05**: Given multiple delivery attempts for the same outbox item, when the dispatcher sends the request, then the `X-Relaybox-Delivery-Id` header remains consistent.\n*   **FR-OBS-01: Health Endpoints**\n    *   **Description**: Expose `/livez` and `/readyz`; `/readyz` checks DB reachability (RULE-OBS-04).\n    *   **AC-OBS-01 (AC-06 in TRD)**: Given the database is unreachable, when `/readyz` is queried, then it returns 503 Service Unavailable.\n*   **FR-OBS-02: Structured Logging & Metrics**\n    *   **Description**: Emit structured JSON logs bound to ctx, and Prometheus metrics for request duration and delivery outcomes with bounded-cardinality labels (`status="delivered|failed|deadletter"`) (RULE-OBS-01, RULE-OBS-03).\n    *   **AC-OBS-02**: Given an event is ingested and delivered, then structured logs with `trace_id` and `span_id` are emitted, and Prometheus metrics for ingestion and delivery are updated with correct labels.\n\n## 2.
